## 제출·배포 준비 및 로컬 커밋 정리 (2026-09-28)

공개 제출용 `t07-submission.md`와 전용 배포 안내 `t07-deploy.md`를 준비했다. 인증 증거·5일 독립 검산·두 날짜 겹침·탈퇴 확인을 연결했다. README의 이전 미완료 표기를 바로잡았다. 앱 기능은 변경하지 않았고 기존 테스트는 반복하지 않았다. 배포 계정·도메인·저장소는 사용자 답변에 따라 미정이다. T06 origin push 차단을 유지하고 외부 배포·push·유료 가입은 하지 않는다.

커밋 후보 50개 파일을 대상으로 금지 경로와 대표 키/토큰·비밀번호 리터럴 패턴을 점검했다. 실제 DB·백업·개인 JSON·가상환경은 포함되지 않았다. 탐지된 두 항목은 테스트용 오답 비밀번호와 내보내기 검증용 설정 표식이며 실제 비밀값이 아니다. 전용 비밀 탐지 도구나 전체 과거 이력의 보안 감사를 수행한 것은 아니다. 최종 공개 직전 원격 저장소 공개 범위도 확인해야 한다. 로컬 커밋에는 기존에 검증한 T07 구현·테스트와 제출 문서만 포함한다. 전체 SHA는 `git rev-parse HEAD`와 완료 응답으로 확인한다. 과거 HEAD/미커밋 표시는 당시 기록이다.

## 5일 원본 독립 검산·브라우저 탈퇴 확인 (2026-09-28)

실제 앱 DB를 SQLite `mode=ro`와 `PRAGMA query_only=ON`으로 열어 oliver의 지정 실험 계획 하나만 선택했다. 삭제 표시되지 않은 할 일의 실행 기록 시작·종료 시각을 읽었다. 앱 생성이나 화면 집계 함수는 호출하지 않았다. 인증 정보·세션·다른 계정 자료·개인 기록 본문은 조회 결과에 출력하지 않았다.

한국 시간 날짜별로 원본 종료−시작을 정수 마이크로초로 계산하고 날짜 경계에서 분리한 뒤, Fraction으로 합계와 평균을 독립 계산했다. 중간 반올림 없이 최종 표시만 소수 첫째 자리 ROUND_HALF_UP을 적용했다. 이번 대상은 5일 11개 기록이며 초 단위 값은 모두 정수다.

| 날짜 | 시작 시각 순 기록별 초 | 일 합계(초) | 일 합계 표시(분) |

**한계:** 위 결과는 저장된 기록의 산술 검산이다. 실제 작업 시간의 정확성을 확인한 결과가 아니다. 9/23의 중복은 합산 616초와 구간 합집합 470초의 차이인 **146초(2분 26초)**로 확인했다. 추가로 9/28에도 합산 552초와 합집합 244초의 차이인 **308초(5분 8초)**가 확인됐다. 9/28 한국 시간 구간은 09:37:20~09:40:24, 09:37:45~09:40:49, 09:38:20~09:41:24다. 중복은 각 구간 길이 합−합집합 길이로 정의했으며, 3중 중복을 쌍별로 중복 계산하지 않았다. 나머지 지정 날짜의 중복은 0초다.

9/23은 실제 시각을 기억하지 못해 원본 유지 및 개선점 기록을 했다는 사용자 보고가 있다. 9/28 중복은 이번 독립 검산의 추가 발견이며 사용자에게 원인 확인을 받은 것은 아니다. 실제 시각을 복원할 근거가 없으므로 두 날짜 모두 원본을 유지했다. 중복 시간을 임의로 빼서 보정 결과를 만들지 않는다. 작업량·난이도도 같지 않으므로 규칙 변경의 효과나 생산성 향상·저하를 단정할 수 없다.

**사용자 수동 확인:** 사용자는 임시 계정의 브라우저 탈퇴와 oliver 기존 자료·5일 기록 보존을 확인했다고 보고했다. HTTP 상태나 모든 쿠키 재사용을 수동 검증했다고 확대하지 않는다. 이 부분은 이전 자동 검사와 별개다.

**다음 배포 단계(미실행):** README의 PythonAnywhere 배포 이력은 T06 자료다. 다음에는 T06 코드/DB를 보존할 T07 별도 배포 위치·URL·DB와 공개 설명 자료 위치부터 확정한다. 전용 실행 환경과 WSGI 앱 설정, 명시적 `PDS_DB_PATH`, HTTPS용 `PDS_COOKIE_SECURE=1`, 공개 경로 밖 DB/백업과 수동 보관·복원 절차를 준비한다. 실제 자료 이전 범위는 별도 결정하며 기존 T06 배포에 덮어쓰지 않는다. 플랫폼의 현재 설정·제약은 배포 단계에서 확인한다. 이후 공개 로그인/설명 자료의 비로그인 접근, 임시 계정 인증·소유권·내보내기·탈퇴, 재시작 후 자료 유지와 HTTPS 쿠키를 확인한다. 이번에는 플랫폼 접속·배포하지 않았다.

남은 필수 항목은 T07 공개 URL·설명 자료와 외부 접근 확인(18), 최종 제출 파일/이력의 비밀값 제외 확인(13), T07 전체 커밋 URL(19)이다. 공개 제출에는 비밀번호·쿠키·세션·실제 DB·백업·개인 JSON을 포함하지 않는다. 인증 증거는 기존 설명서에 있고 산술 검산(17)과 탈퇴 브라우저 확인(11)은 이번 기록으로 보완됐다. 이번에는 문서만 갱신했으며 코드·DB 수정, 재가져오기, 테스트 재실행, 배포·push는 하지 않았다. 아래 과거의 미확인 표시는 각 기록 당시 상태다.

## 계정 삭제 구현 완료 (2026-09-28)

`auth.py:delete_account()`의 `GET /account/delete`에서 삭제 범위·복구 불가·탈퇴 전 내보내기·백업 처리 안내를 보여준다. `templates/base.html`에 계정 삭제 링크, `templates/account_delete.html`에 현재 비밀번호와 필수 동의 입력을 추가했다. POST는 기존 CSRF 검사와 scrypt 비밀번호 확인을 거치며 삭제 대상은 서버의 `g.user`로만 결정한다.

쓰기 잠금 후 비밀번호를 다시 확인하고 연결된 11종 자료(삭제 표시된 할 일 포함), 모든 세션, 계정을 하나의 트랜잭션에서 삭제한다. 오류는 전체 롤백하고 503을 반환한다. 기존 백업·다운로드 JSON은 자동 삭제하지 않는다. 현재 자동 보관 기한/자동 정리 기능은 없으며 운영자가 수동 관리한다. 백업 복원 시 탈퇴 자료와 세션의 재등장 방지도 수동 확인이 필요하고 자동화되지 않았다. 앱의 탈퇴 취소/복구 기능은 없다.

## 제출 준비 상태 갱신 (2026-09-28)

**사용자 브라우저 확인:** 실제 기록 날짜는 9/18·9/21·9/22·9/23·9/28로 서로 다른 5일이다. 규칙 변경은 9/22 16:11:58(한국 시간) 저장됐고, 화면에서 3일차 작업 전이라는 시점 검증을 통과했다. 화면 표시값은 변경 전 합계 6.1분·하루 평균 3.1분, 변경 후 합계 31.7분·하루 평균 10.6분이다.

**기록 한계:** 사용자는 9/23 기록에 총 2분 26초의 시간 겹침이 있고 실제 시각을 기억하지 못해 원본을 유지했으며, 개선점에 한계를 적었다고 보고했다. 위 값은 겹치는 구간도 합산하는 화면의 참고값이다. 정확한 최종 작업 시간이나 검증된 규칙 변경 효과로 표현하지 않는다. 임의 차감·시각 보정도 하지 않았다. 원래 정밀도에 따른 실제 5일 합계·평균의 수동 검산은 아직 확인되지 않았다.

**제출 전 남은 항목:** 체크리스트 11번 계정 삭제 기능과 자료·세션·백업 처리 안내, 17번 실제 자료 수동 검산 및 겹침 한계 명시, 18번 T07 공개 로그인 주소·공개 설명 자료와 외부 비로그인 접근 확인, 19번 T07 전체 커밋 URL, 13번 최종 제출물 비밀값 점검이다. 인증 설명서 여섯 항목과 요청 방식·경로·상태·소스 증거는 `t07-auth.md`에 이미 있다. 공개 운영에서 확인한 증거로 확대하지 않는다. 계정 삭제는 현재 체크리스트상 기능과 안내 모두 요구하므로 안내만으로 완료 처리하지 않는다.

**이번 확인 범위:** 문서와 필요한 인증/README 근거, Git 상태만 확인했다. HEAD는 여전히 T06 기준 `25809d886e4a53c8e0efa8c75100e40d485bae4d`이고 T07 변경은 미커밋 상태다. DB·다운로드 JSON을 재검사하지 않았고 코드·실제 자료 변경, 재가져오기, 배포·push, 테스트 재실행은 하지 않았다. 68개 통과는 이전 실행 결과다. 아래 1일차·이력 0개라는 내용은 당시 기록으로 보존한다.

**다음 우선 작업:** 계정 삭제 시 자료·세션·백업 처리 정책과 사용자 안내를 정하고, 그 정책에 맞는 계정 삭제 기능을 구현·검증한다. 남아 있는 명확한 필수 기능이므로 공개 배포와 최종 커밋 전에 처리한다.

## 재개 후 마무리 확인 (2026-09-21)

현재 변경 내역과 아래 최신 구현 기록을 확인했다. 실제 대상 `instance/pds.sqlite3`를 읽기 전용으로 열어 `review_rule_changes`·`review_rule_evidence` 및 필요한 열이 이미 적용되어 있음을 확인했다. 두 테이블은 각각 0행이며 계획 4개·실행 기록 4개다. SQLite 무결성 검사는 `ok`, 외래키 위반은 0건이고 아래 기록된 적용 전 백업도 존재한다. 추가 마이그레이션이나 DB 쓰기는 하지 않았다.

구현과 실제 DB 적용은 완료 상태다. 코드 수정과 테스트 재실행은 하지 않았으며 **68개 통과는 직전 실행 결과**다. 이번에는 이 완료 확인만 문서에 추가했다. 남은 일은 서버 재실행 후 사용자의 새 화면 확인과 실제 날짜별 기록 진행이다. 실제 규칙 변경·사용 기록 생성, 계정 삭제, 배포·push는 하지 않았다.

기존 돌아보기 아래에 날짜별 분석을 추가했다. 계정 삭제·배포·push는 하지 않았다. 실제 계정의 계획·실행 기록·시각은 바꾸지 않았으며, 실제 규칙 변경이나 나머지 4일 자료도 대신 등록하지 않았다.

### 구현한 동작

- `review_experiment.py`가 로그인한 사용자의 선택한 계획에 속한 기록만 처리한다. 삭제된 할 일의 기록은 기존 돌아보기와 같이 제외한다.
- 원래 UTC 시작·종료 시각 차이를 **정수 마이크로초**로 계산하고 **Asia/Seoul 자정**에서 나눈다. 분·합계·평균은 Fraction으로 유지하며 화면에 표시할 때만 **소수 첫째 자리, 사사오입(ROUND_HALF_UP)**으로 반올림한다. 같은 날짜의 여러 기록은 모두 합산하며 중복 시간 구간을 합집합으로 바꾸지는 않는다.
- 종료가 정확히 자정이면 다음 날의 0분 행을 만들지 않는다. 기록 없는 날짜를 채우지 않는다. 사용자가 실제 저장한 0초 기록은 해당 날짜에 근거가 있는 0분 기록으로 구분한다.
- 날짜별 펼침 영역에서 그 날짜에 포함된 구간 시각·기여 시간·원본 실행 기록 링크를 확인할 수 있다.
- 현재까지 전체 합계와 **실제 기록일 수를 분모로 한 평균**은 진행 중 값으로 표시한다. 5일 결과는 실제 기록 날짜 5개가 선택된 경우에만 보여준다. 기록 날짜가 5개보다 많으면 자동으로 고르지 않고 사용자가 5개를 선택해야 한다. 포함 날짜와 1~5일차 순서를 화면에 표시한다.
- 기존 7개 전체 집계는 저장된 `actual_minutes` 기준을 유지한다. 새 날짜별 분석은 시작·종료 시각 기준이므로 기록별 기존 반올림과 차이가 날 수 있음을 화면에 설명한다. 기존 데이터나 기존 합계의 계산법을 몰래 바꾸지 않았다.

### 규칙 변경과 최종 비교의 조건

- `GET/POST /review/rules`에서 사용자가 변경 전 규칙·변경 후 규칙·이유·근거 1/2일차 날짜를 직접 입력하고 기록 완료를 확인한다. 시각은 서버가 UTC로 저장하고 화면에는 한국 시간으로 표시한다. 클라이언트가 보낸 저장 시각·사용자 ID는 사용하지 않는다.

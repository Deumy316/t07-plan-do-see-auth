## 제안하는 구성

**프런트엔드: HTML·CSS·기본 JavaScript / 서버: Python Flask / DB: SQLite** 한 가지 구성으로 시작합니다.

Flask 서버 하나가 HTML 화면과 폼 저장·조회 요청을 함께 처리합니다. 서버가 Python 내장 `sqlite3`로 실제 DB 파일에 기록합니다. JavaScript는 기존 폼 주소로 저장을 요청하고 저장 중·성공·실패 상태를 표시합니다. JavaScript 없이도 일반 폼 저장이 동작합니다. 일회성 성공 알림에만 sessionStorage를 사용하고 계획 데이터는 서버 DB에 저장합니다. 별도의 프런트엔드 빌드 도구나 Node.js, DB 서버 설치는 필요하지 않습니다. JSON API와 localStorage 저장은 사용하지 않습니다.

로컬 개발에서는 Flask 3.1.3과 tzdata 2026.4를 Python 3.14.7 가상환경에 설치했고 테스트를 통과했습니다. 간접 의존성까지 `requirements.txt`에 버전을 고정했습니다. 현재 공개 운영 환경은 PythonAnywhere의 Python 3.13·Flask·SQLite입니다.

### 로컬 실행: 내 컴퓨터에서 개발

PowerShell에서 다음 두 줄을 실행합니다. 현재 폴더에는 가상환경과 패키지가 이미 준비되어 있습니다. 활성화 없이 가상환경의 실행 파일을 직접 지정합니다.

```powershell
cd C:\work\aleph\t06-plan-do-see
.\.venv\Scripts\python.exe app.py
```

브라우저에서 **http://127.0.0.1:5000** 을 엽니다. 터미널을 켜 둔 채 사용하고 종료할 때는 `Ctrl+C`를 누릅니다. 같은 명령으로 다시 실행하면 기존 계획이 유지됩니다. 포트가 사용 중이면 기존 서버를 종료하거나 `$env:PDS_PORT = "5001"`로 설정하고 5001 주소로 접속합니다. 이 명령으로 실행한 로컬 서버는 내 컴퓨터에서만 접속하는 개발용 서버이며, PythonAnywhere 공개 사이트와 별개입니다.

새 컴퓨터에서 처음 준비하거나 가상환경을 다시 만들 때만 아래 명령을 먼저 실행합니다. Windows 전역 `python`은 Store 별칭이므로 생성에는 확인된 `py`를 사용합니다.

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

사용 순서: **새 계획 → 항목 입력 → 계획 저장 → 상세 화면 → 계획 수정 → 수정 저장 → 수정 이력의 버전 펼치기**입니다. 시작일·종료일은 필수이고 종료일은 시작일 이상이어야 합니다. 예상 시간은 정수 분이며 0을 허용합니다. 다른 창에서 먼저 수정한 경우 충돌 안내가 나오므로 상세 화면으로 돌아가 최신 내용을 확인합니다.

기본 DB는 `instance/pds.sqlite3`입니다. 첫 실행 때 빈 테이블을 만들고 기존 자료는 지우지 않습니다. 위치를 변경하려면 서버 종료 후 같은 PowerShell 창에서 설정합니다.

```powershell
$env:PDS_DB_PATH = "C:\work\aleph\t06-plan-do-see\instance\my-plans.sqlite3"
.\.venv\Scripts\python.exe app.py
```

경로를 바꾸면 별도 DB를 열며 기존 자료를 자동으로 옮기지는 않습니다. 상대 경로는 프로젝트 폴더 기준입니다. 기본 경로로 돌아가려면 `Remove-Item Env:PDS_DB_PATH -ErrorAction SilentlyContinue` 후 서버를 다시 실행합니다. `.env` 파일은 자동으로 읽지 않으며 PowerShell 환경변수를 사용합니다.

### 구현 파일과 저장 규칙

- `app.py`: Flask 경로, 입력 검증, 트랜잭션, 한국 시간 표시
- `tasks.py`: 할 일 관리, 검색·필터·정렬, 완료 요청의 트랜잭션 처리
- `executions.py`: 실행 기록 입력·목록, 한국 시간→UTC 변환, 실제 시간 계산, 요청 중복 방지
- `review.py`: 선택한 계획의 집계·근거 조회, 개선점 저장 및 연결된 다음 계획 조회
- `export_data.py`: 전체 자료의 읽기 전용 JSON 다운로드와 계획별 집계
- `schema.sql`: 계획·수정 이력, 할 일·태그·상태 요청·완료 이벤트 테이블
- `templates/`, `static/`: 한국어 화면, 다크 테마, 저장 버튼 동작
- `contracts/pds-schema-v2.json`: 구현한 테이블의 필드·관계·단위·날짜 및 완료 재시도 규칙
- `tests/test_plans.py`, `tests/test_tasks.py`: 별도 DB를 사용하는 자동 검증

생성 때 버전 1을 저장합니다. 수정 시 ID와 생성 시각을 유지하고 버전을 증가시키며, 현재 계획과 전체 이력 스냅샷을 한 트랜잭션으로 저장합니다. 이전 버전은 변경하지 않습니다. SQL 값은 매개변수로 전달하고 사용자 입력은 HTML 이스케이프합니다. 시각은 UTC로 저장하고 화면에는 Asia/Seoul 기준으로 표시합니다. 날짜만 있는 값은 시간대 변환 없이 표시합니다.

`.gitignore`는 `.venv/`, 비밀값 `.env` 계열, `instance/`, DB와 SQLite 저널 파일 등을 제외합니다. Git 저장소는 `main` 브랜치로 초기화했으며 원격 소스 저장소는 [Deumy316/t06-plan-do-see](https://github.com/Deumy316/t06-plan-do-see)입니다.

기존 남색 배경과 보라색 강조색을 유지했습니다. 전체 최대 너비를 1320px로 제한하고 PC 계획 목록은 두 열, 입력·상세는 본문과 보조 정보로 배치합니다. 모바일에서는 한 열로 전환합니다. 입력 항목은 내용·기간과 우선순위·성공 기준으로 묶었으며, 수정 이력은 버전과 저장 시각을 구분한 타임라인입니다. 긴 내용은 줄바꿈하고 키보드 초점·비활성화·오류 상태를 표시합니다. 서버 경로, DB 구조, 저장 데이터는 디자인 변경 대상이 아닙니다.

### 할 일 사용 방법

같은 실행 명령으로 서버를 시작한 후 **할 일** 메뉴 또는 `http://127.0.0.1:5000/tasks`로 이동합니다.

1. 관리할 계획을 선택하고 **계획·조건 적용**을 누릅니다. 계획이 없으면 먼저 계획을 만드는 안내가 나옵니다.
2. **할 일 추가**에서 제목·내용·마감일·우선순위·태그·예상 시간을 입력합니다. 제목과 계획은 필수이며 예상 시간은 0 이상의 정수 분입니다. 마감일은 비워 둘 수 있습니다.
3. 태그는 쉼표로 구분합니다. 앞뒤 공백과 빈 태그를 제거하고 같은 태그는 하나만 저장합니다. 태그의 대소문자는 구분합니다.
4. 목록에서 **수정**, **완료로 변경**, **완료 취소**를 사용할 수 있습니다. 상태는 반전하지 않고 버튼에 명시한 상태로 변경합니다. 연결된 계획은 수정 화면에서 다른 계획으로 옮길 수 없습니다.
5. **삭제**를 누르면 별도 확인 화면이 열립니다. **삭제 확인**을 눌러야 삭제되며, 취소하면 그대로 남습니다. 삭제한 항목은 화면에서 복원할 수 없습니다.

검색은 제목 또는 내용의 부분 문자열을 찾습니다. `%`, `_`는 검색 와일드카드가 아닌 글자로 취급합니다. 상태·우선순위·태그 필터는 검색과 동시에 적용됩니다. 태그 필터는 정확히 일치하는 태그를 찾습니다.

기본 정렬은 마감일 오름차순이며 마감일이 없는 항목은 마지막입니다. 우선순위순은 높음→보통→낮음, 최신 생성순은 생성 시각 내림차순입니다. 모든 정렬에서 동률은 고유 ID 오름차순으로 고정합니다. 화면에 현재 정렬 기준과 조건에 맞는 실제 항목 수를 표시합니다.

### 완료 요청의 재시도와 재완료 규칙

상태 변경 주소는 `POST /tasks/<고유 ID>/state`입니다. `target_status`는 `completed`(완료) 또는 `active`(진행 중), `version`은 화면에서 읽은 현재 버전, `request_id`는 요청별 UUID입니다. 일반 수정으로 상태를 바꿀 수 없습니다.

- **재시도:** 같은 요청은 `request_id`, 할 일 ID, 목표 상태, 버전을 그대로 다시 보냅니다. 이미 성공한 요청이면 새 기록을 만들거나 현재 상태를 변경하지 않고 목록으로 이동합니다. 완료 취소 후 옛 완료 요청이 재전송되어도 다시 완료시키지 않습니다.
- **새 요청:** 새로운 사용자 동작은 새 `request_id`와 최신 버전을 사용합니다. 완료 취소 후 재완료도 이 방식으로 새 완료 이벤트를 남깁니다.
- **오래된 요청:** 새 요청 식별자라도 버전이 오래됐으면 HTTP 409로 거부합니다. 동일 식별자에 다른 요청 내용을 넣어도 409입니다.
- **이미 같은 상태:** 최신 버전으로 현재와 같은 상태를 요청하면 처리 영수증만 저장합니다. 완료 이벤트, 버전, 완료·수정 시각은 추가·변경하지 않습니다.
- **동시 요청:** `BEGIN IMMEDIATE`로 쓰기 처리를 직렬화하고, 현재 상태 변경·요청 영수증·완료 이벤트 저장을 하나의 트랜잭션으로 처리합니다. 같은 버전의 서로 다른 동시 요청은 하나만 변경에 성공하고 나머지는 409입니다.

DB에서도 요청 ID 기본키, 완료 이벤트의 요청 ID 고유 제약, `(task_id, task_version)` 고유 제약으로 중복을 막습니다. 완료 취소는 완료 시각을 비우고 상태 버전을 증가시키며, 기존 완료 이벤트는 감사 기록으로 남깁니다. 이벤트 수를 현재 완료 개수로 사용하지 않습니다. 실행 시간·실행 기록을 임의로 생성하지 않습니다.

### 할 일 DB 추가와 검증 결과

서버 시작 시 기존 DB에 `tasks`, `task_tags`, `task_state_requests`, `task_completion_events`와 조회 인덱스를 추가합니다. 기존 `plans`, `plan_versions`를 삭제하거나 초기화하지 않습니다. 삭제는 `deleted_at`을 기록하는 방식이며 목록·검색 결과 수·태그 선택지에서 제외합니다. 돌아보기에서도 삭제된 할 일과 그 실행 기록을 제외하며, 완료 수는 과거 완료 이벤트가 아닌 현재 상태로 계산합니다.

- 추가·수정·완료·완료 취소·삭제 확인, 삭제 후 목록 제외

### 초기 배포 제안: Render (현재 운영 환경 아님)

다음 내용은 프로젝트 준비 단계에 검토한 대안입니다. 실제 배포는 위 PythonAnywhere 구성을 사용하며 Render 서버·유료 디스크·Waitress 구성으로 운영 중이라는 뜻이 아닙니다.

- 당시 제안한 배포 대상은 **Render 유료 Web Service + 영구 디스크**였습니다. 현재 운영에는 이 구성을 사용하지 않습니다.
- 공개 서버는 Flask 개발 서버 대신 Waitress로 실행하는 구성을 제안합니다. Waitress는 Windows도 직접 지원하므로 로컬에서 배포 실행 방식을 확인하기 좋습니다. [Flask의 Waitress 안내](https://flask.palletsprojects.com/en/stable/deploying/waitress/)
- 영구 디스크를 `/var/data`에 연결하고 `PDS_DB_PATH=/var/data/pds.sqlite3`로 설정합니다. 디스크 내부에 DB를 두어 재시작·재배포 후에도 자료를 유지합니다.
- Render의 기본 파일 시스템은 임시 공간입니다. 무료 Web Service에는 영구 디스크를 연결할 수 없으므로, 무료 서버의 일반 폴더에 SQLite를 저장하는 방식으로는 영속성 요구를 충족하지 못합니다. 서비스와 디스크 비용은 배포 시 확인합니다. [무료 서비스 제한](https://render.com/docs/free), [영구 디스크 안내](https://render.com/docs/disks)
- 영구 디스크는 빌드 단계에서 접근할 수 없으므로 DB 생성·변경은 서버 시작 시 수행하는 절차로 설계합니다. 하나의 서버 인스턴스로 운영하고, 동시 쓰기는 짧은 트랜잭션으로 처리합니다.
- 로컬 DB와 공개 DB는 별개의 자료입니다. 소스 배포로 로컬 DB가 자동 복사되지 않습니다. 배포 후에는 공개 서버에서 저장·새로고침·재시작·재배포 유지 여부를 확인합니다.
- 영구 디스크만으로 백업을 대신하지 않습니다. 전체 내보내기와 별도 백업·복구 절차를 마련합니다.

## 최종 요구사항

- **계획:** 기간, 우선순위, 성공 기준, 예상 시간을 저장하고 수정할 수 있어야 합니다. 수정 전후 내용과 변경 시각을 이력으로 보관합니다.
- **계획에 연결된 할 일:** 추가, 수정, 완료, 완료 취소, 삭제를 지원합니다. 마감일, 우선순위, 태그, 예상 시간과 검색·필터·정렬 기능을 제공합니다.
- **할 일에 연결된 실행 기록:** 시작·종료 시각, 실제 소요 시간, 막힌 이유를 저장합니다. 실제 실행 값을 기록해도 원래 계획의 예상 값은 덮어쓰지 않습니다.
- **완료 중복 방지:** 연속 클릭, 요청 재전송, 동시 요청에서도 완료 기록과 집계가 중복되지 않아야 합니다. 화면 버튼 처리뿐 아니라 서버와 DB에서도 보장합니다.
- **돌아보기:** 할 일 수, 완료·지연·막힘 수, 예상·실제 시간 및 차이를 보여 줍니다. 집계 숫자를 누르면 해당 계산의 근거 기록을 확인할 수 있어야 합니다.
- **개선점 연결:** 돌아보기에서 정한 개선점을 다음 계획에 연결하고 출처를 추적할 수 있어야 합니다.
- **영구 저장:** 서버의 실제 DB에 저장하고 새로고침 후에도 유지합니다. localStorage만 사용하는 방식은 허용하지 않습니다.
- **전체 내보내기:** 계획, 수정 이력, 할 일, 태그, 실행 기록, 완료·취소 이력, 돌아보기와 개선점 연결을 관계와 함께 JSON 파일 하나로 내보냅니다.
- **공개 앱 안내:** 로그인 없이 접근합니다. 첫 화면에 누구나 자료를 볼 수 있고 공용 자료를 수정할 수 있다는 안내와 개인정보·비밀정보를 입력하지 말라는 안내를 표시합니다.
- **안전한 입력 표시:** 사용자 입력은 스크립트로 실행되지 않고 글자로 표시합니다. 템플릿 자동 이스케이프와 DOM의 `textContent` 등을 사용하고 서버에서 입력을 검증합니다.
- **비밀값 관리:** 비밀값은 소스와 Git에 넣지 않고 환경변수로 관리합니다. 예시 설정에는 실제 비밀값을 넣지 않습니다.
- **계약 문서:** 최종 DB 구조와 날짜 규칙을 `contracts/pds-schema-v2.json`에 기록하고 구현과 일치시킵니다.
- **최종 제출:** 실제 공개 앱 URL과 제출 소스의 고정 commit URL을 제공합니다. 변경될 수 있는 브랜치 주소만으로 대체하지 않습니다.

## 단계별 구현 순서

### 1. 데이터 규칙과 계약 확정

`contracts/pds-schema-v2.json`에 계획과 이력의 테이블, 필드, 자료형, 필수 여부, 기본값, 외래키, 고유 제약, 삭제 정책과 날짜 규칙을 기록했습니다. 이후 기능을 추가할 때 확장합니다.

계획과 수정 이력, 할 일과 태그, 실행 기록, 완료·취소 이력, 돌아보기, 개선점과 다음 계획의 연결을 구분합니다. 실행 기록은 여러 건을 허용하고, 삭제 후 이력과 집계가 어떻게 유지되는지도 정합니다.

현재 계획과 실행 기록 규칙은 계약에 기록했습니다. 돌아보기 집계 규칙은 해당 기능 구현 전에 확정합니다.

- 날짜만 있는 기간·마감일은 `YYYY-MM-DD`, 사용자 표시와 일자 경계는 `Asia/Seoul` 기준입니다.
- 시작·종료·생성·수정 시각은 UTC의 ISO 8601 문자열(`Z` 포함)로 저장하고 화면에서 한국 시간으로 변환합니다.
- 종료 시각은 시작 시각 이상이어야 합니다. 예상 시간은 정수 분, 실제 실행 시간은 분 단위 소수 둘째 자리까지 저장합니다. 정확한 반올림과 시간대 규칙은 아래 실행 기록 절에 기록했습니다.
- 계획 기간의 양 끝 날짜를 포함하며, 기간 조회는 한국 시간 시작일 00:00 이상부터 종료일 다음 날 00:00 미만으로 계산합니다.
- 진행 중 실행의 실제 시간, 완료 후 마감일을 넘긴 건의 지연 처리, 막힘 수의 중복 제거, 삭제 건의 집계 포함 여부를 확정합니다.
- 집계 대상 기간, 기준 시각, 포함 상태, 예상 시간의 기준 버전과 차이(`실제 - 예상`)를 명시합니다. 숫자와 근거 목록은 동일한 조건으로 조회합니다.

### 2. 실행 환경과 DB 기반 준비

Python 가상환경과 패키지 설치·호환성 확인을 완료했습니다. 의존성 버전, 로컬 실행 명령, 환경변수 예시를 문서화했고 DB 연결·외래키·트랜잭션 처리를 구현했습니다. Git 초기화와 원격 연결도 완료했습니다. 후속 DB 변경을 위한 마이그레이션 체계는 추후 준비합니다.

### 3. 계획과 수정 이력 구현

계획 생성·수정·조회와 수정 이력을 구현했고, 이전 값 보존과 트랜잭션 롤백을 검증했습니다.

### 4. 할 일과 완료 처리 구현

할 일 추가·수정·삭제, 태그, 마감일, 검색·필터·정렬 및 완료·완료 취소를 구현했습니다. 요청 ID 고유 제약, 버전 확인, 트랜잭션으로 연속·동시 요청의 중복 완료를 방지합니다. 재시도와 정상 재완료 규칙 및 검증 결과는 위 할 일 절에 기록했습니다.

집계는 유효한 현재 상태와 기록을 기준으로 계산하여 요청마다 카운터를 무조건 증가시키지 않습니다.

### 5. 실행 기록 구현

### 실행 기록 사용 방법과 계산 규칙

기존과 같이 `.\.venv\Scripts\python.exe app.py`로 실행한 뒤 **실행 기록** 메뉴 또는 `http://127.0.0.1:5000/executions`를 엽니다.

1. 계획을 선택하고 **선택한 계획 보기**를 누릅니다.
2. 해당 계획에 연결된 할 일을 선택합니다. 진행 중·완료 상태 모두 기록할 수 있습니다. 삭제된 할 일은 선택할 수 없습니다.
3. 시작·종료 시각을 한국 시간으로 입력하고 수행 내용을 작성합니다. 막힌 이유는 선택입니다. 실제 시각이나 수행 내용은 자동으로 채우지 않습니다.
4. **실행 기록 저장**을 누르면 같은 계획의 기록 목록에 할 일 제목과 함께 표시됩니다. 하나의 할 일에 여러 기록을 추가할 수 있습니다. 목록의 **수정** 버튼으로 기존 기록을 수정할 수 있으며 삭제는 제공하지 않습니다.

입력 형식은 `YYYY-MM-DDTHH:mm` 또는 `YYYY-MM-DDTHH:mm:ss`이며 초 생략 시 00초입니다. 브라우저나 컴퓨터 시간대와 관계없이 `Asia/Seoul`로 해석하고 UTC의 ISO 8601 `Z` 형식으로 저장합니다. 화면에는 한국 시간으로 표시합니다. 시간대 접미사·소수 초·유효하지 않은 날짜는 거부합니다. 과거 서머타임 때문에 존재하지 않거나 두 가지 UTC 시각으로 해석되는 한국 시각도 거부합니다.

서버는 UTC 종료−시작의 정수 초를 계산합니다. 종료가 빠르면 거부하고 같은 시각은 0분을 허용합니다. `실제 분 = ((소요 초 × 100 + 30) // 60) / 100`으로 소수 셋째 자리에서 반올림하여 소수 둘째 자리까지 저장·표시합니다. 예: 1초는 0.02분, 30분 30초는 30.50분입니다. 시작·종료 시각 자체는 반올림하지 않습니다. 클라이언트가 실제 시간을 임의로 보내도 계산에 사용하지 않습니다.

폼을 열 때 UUID 요청 식별자를 발급합니다. 같은 폼 연타·재전송은 같은 식별자를 사용하고 `BEGIN IMMEDIATE` 트랜잭션과 `UNIQUE(request_id)` 제약으로 한 건만 저장합니다. 같은 식별자와 정규화된 할 일·시각·내용·막힌 이유가 같으면 기존 성공 요청으로 처리하며, 내용이 다르면 HTTP 409로 거부합니다. 새 기록을 의도적으로 입력할 때는 새 폼의 새 식별자를 사용합니다. 서로 다른 식별자는 같은 내용이어도 별개의 사용자 기록으로 허용합니다.

저장은 `execution_records`에만 쓰며 기존 계획·수정 이력·할 일 상태·예상 시간·완료 이벤트를 변경하지 않습니다. 목록은 선택한 계획에 한정하여 시작 시각 내림차순, 동률 ID 오름차순입니다. 할 일 삭제 후 기존 실행 기록은 DB에 남지만 목록에서는 제외됩니다. 서버 시작 시 테이블과 인덱스만 추가하며 기존 DB를 초기화하지 않습니다.

### 돌아보기 사용 방법과 집계 기준

**돌아보기** 메뉴 또는 `http://127.0.0.1:5000/review`에서 계획을 선택하고 **선택한 계획 보기**를 누릅니다. 각 집계 숫자를 클릭하거나 키보드로 선택해 펼치면 계산에 사용한 할 일·실행 기록을 확인할 수 있습니다.

대상은 **선택한 계획에 연결된 삭제되지 않은 할 일 전체**입니다. 기간 필터는 없으며 화면에 한국 시간 기준 오늘 날짜와 시간 단위(분)를 명시합니다.

| 표시 | 계산 기준 | 펼쳤을 때의 근거 |
| --- | --- | --- |
| 계획한 할 일 | 대상 할 일 수. 계획 자체의 개수가 아님 | 대상 할 일 전체 |
| 완료 | 현재 상태가 완료인 대상 할 일 수 | 완료 할 일 |
| 지연 | 미완료이며 마감일이 한국 시간 오늘보다 앞선 할 일 수 | 해당 할 일과 마감일 |
| 막힘 | 공백이 아닌 막힌 이유가 있는 실행 기록이 하나 이상 연결된 할 일 수 | 중복 없는 할 일 목록과 해당 막힘 기록 |
| 예상 시간 | 대상 할 일의 현재 예상 시간 합계 | 할 일별 예상 분 |
| 실제 시간 | 대상 할 일에 연결된 모든 실행 기록의 저장된 소요 시간 합계 | 기록별 실제 분·한국 시작/종료 시각·내용 |
| 차이 | 실제 시간 − 예상 시간. 음수도 허용 | 예상·실제 내역 모두와 계산식 |

오늘 마감·미래 마감·마감일 없음은 지연에서 제외합니다. 막힘 판단은 앞뒤 공백뿐 아니라 탭·개행·전각 공백 등 `str.strip()`으로 제거되는 공백만 있는 이유도 제외합니다. 같은 할 일의 막힘 기록이 여러 개여도 막힘 수는 한 번만 셉니다. 막힘은 완료나 지연과 겹칠 수 있어 세 수를 더해 전체로 해석하면 안 됩니다.

예상 시간은 실행 기록과 합쳐서 합산하지 않고 할 일 목록에서 한 번씩 더합니다. 실제 시간은 각 실행 기록에 저장된 소수 둘째 자리까지의 분 값을 `Decimal`로 합산합니다. 계획 자체의 예상 시간이나 과거 완료 이벤트 개수는 이 집계에 사용하지 않습니다. 데이터가 없으면 모두 0이며 근거도 빈 목록으로 표시합니다.

숫자와 근거는 한 번의 SQLite 읽기 트랜잭션으로 확보한 동일 자료에서 계산합니다. 펼침 시 별도 조회하지 않으므로 화면 내 숫자와 근거가 일치합니다. 최신 변경과 날짜를 반영하려면 새로고침합니다. 돌아보기 GET 조회와 집계는 읽기 전용이며, 개선점 저장 POST는 별도 개선점 테이블에 기록합니다.

### 개선점 → 다음 계획 연결

1. 돌아보기에서 계획을 선택합니다. 집계 아래 **다음 계획에서 고칠 점**에 직접 내용을 입력하고 **개선점 저장**을 누릅니다.
2. 개선점은 선택한 계획에 연결해 SQLite에 저장되며 새로고침 후에도 남습니다. 저장할 때마다 별도의 개선점으로 추가합니다. 이번 단계에는 개선점 수정·삭제 기능은 없습니다.
3. 저장된 개선점의 **이 내용으로 다음 계획 만들기**를 누르면 기존 계획 작성 화면으로 이동하고 내용만 미리 채워집니다. 이 버튼만으로 계획을 생성하지 않습니다.
4. 제목·기간·우선순위·성공 기준·예상 시간을 확인하고 **계획 저장**을 누릅니다. 제목·기간·성공 기준은 처음에는 비어 있으며, 우선순위와 예상 시간은 기존 기본값(보통, 0분)입니다. 미리 채워진 내용도 수정할 수 있습니다.
5. 이전 계획의 돌아보기에 있는 해당 개선점 아래 **연결된 다음 계획**에서 새 계획 상세로 이동합니다. 새 계획의 제목을 나중에 수정해도 연결은 유지됩니다.

`review_improvements`는 개선점 ID·이전 계획 ID·내용·UTC 생성 시각을 보관합니다. `next_plan_links`는 다음 계획 ID·이전 계획 ID·개선점 ID·연결 생성 시각을 보관합니다. 개선점과 이전 계획이 일치하도록 복합 외래키로 보호하며, 다음 계획 한 개의 출처는 하나입니다. 한 개선점에서 사용자가 별도로 저장한 다음 계획 여러 개를 연결할 수 있습니다.

계획 작성 폼의 숨김 `source_improvement`를 서버에서 확인합니다. 존재하지 않는 개선점은 거부하고, 입력 오류가 발생하면 사용자가 작성한 내용과 출처를 유지합니다. 새 계획·최초 수정 이력·연결은 하나의 DB 트랜잭션으로 저장하므로 연결 저장 실패 시 계획 생성도 취소됩니다. 원래 계획이나 원래 수정 이력은 변경하지 않습니다. 새 테이블만 추가하고 기존 사용자 자료를 초기화하거나 개선점을 임의로 채우지 않습니다.

- 원래 계획과 수정 이력 보존, 잘못된 출처·빈 개선점 거부
- 입력 오류 시 내용과 출처 유지, 연결 INSERT 실패 시 새 계획·이력 전체 롤백

개선점 기능 개발 당시에는 서버 요청·응답 HTML·별도 DB로 검증했습니다. 이후 PythonAnywhere 공개 사이트에서 다음 계획 연결을 사용자가 확인했습니다. 모바일 기기 검증 결과는 기록하지 않았습니다.

### 전체 자료 내보내기

모든 화면 하단의 **전체 자료 내보내기** 버튼을 누르거나 `http://127.0.0.1:5000/export.json`을 열면 `pds-export-<UTC 시각>.json` 파일 하나를 다운로드합니다. 현재 선택한 계획과 검색 조건에 관계없이 **전체 계획의 모든 자료**를 포함합니다. UTF-8 JSON이며 한글을 그대로 기록합니다.

파일의 최상위 형식은 다음과 같습니다.

| 키 | 내용 |
| --- | --- |
| `schema_version` | DB 계약 버전 문자열 `"2"` |
| `export_format_version` | 내보내기 형식 버전 문자열 `"1"` |
| `exported_at` | 내보내기 DB 스냅샷의 기준 시각, UTC ISO 8601 `Z` |
| `aggregation_as_of` | 모든 집계의 기준 시각, `exported_at`과 동일 |
| `timezone` | 저장 시각 UTC, 표시·오늘 날짜 경계 Asia/Seoul |
| `time_units` | 예상·실제 시간 단위와 집계 숫자 표현 방식 |
| `review_rules` | 계획별 돌아보기 집계 규칙 |
| `data` | 아래 9개 테이블 이름을 키로 갖는 전체 자료 배열 |
| `plan_reviews` | 모든 계획의 `plan_id`, `calculated_at`, `today_seoul`, `metrics` |

`data`에는 `plans`, `plan_versions`, `tasks`, `task_tags`, `task_state_requests`, `task_completion_events`, `execution_records`, `review_improvements`, `next_plan_links`가 포함됩니다. 필드는 계약 문서의 `export_format.data_fields`에 명시한 목록입니다. 고유 ID·외래키·null·삭제 시각을 그대로 보존합니다. 완료 취소 요청과 과거 완료 이벤트도 포함하므로 완료 이력이 유실되지 않습니다.

`plan_reviews.metrics`는 `planned`, `completed`, `overdue`, `blocked`, `estimated`, `actual`, `difference`를 담습니다. 앞의 다섯 값은 JSON 정수이며, `actual`과 `difference`는 합계의 정밀도를 지키기 위한 **분 단위 십진수 문자열**입니다. 예: `"0.05"`, `"-9.95"`. 원본 실행 기록의 `actual_minutes`는 JSON 숫자입니다. 큰 정수를 외부 도구로 읽을 때는 정밀도를 보존하는 파서를 사용해야 합니다.

삭제된 할 일과 연결된 자료도 원본 배열에 남지만 계획별 집계에서는 기존 규칙대로 제외합니다. 예상 시간은 할 일당 한 번, 실제 시간은 해당 실행 기록별로 합산합니다. 완료는 현재 상태로 계산하고, 지연은 모든 계획에 동일하게 적용한 한국 날짜를 기준으로 계산합니다. 빈 계획도 0 집계를 포함하며 계획 자체가 없으면 `plan_reviews`는 빈 배열입니다.

내보내기는 하나의 SQLite 읽기 트랜잭션에서 전체 자료를 확보하고, 그 자료로 돌아보기와 동일한 계산 함수를 호출합니다. 데이터를 변경하거나 서버에 다운로드 파일을 저장하지 않습니다. 테이블·필드는 허용 목록으로 제한하며 비밀번호, 환경변수, 앱 설정, 서버 파일 경로, 계약 파일 자체는 출력하지 않습니다. 사용자가 직접 입력한 자료는 원문 그대로 포함합니다.

### 내보내기 검증 결과

별도 DB에서 **내보내기 3개 + 기존 26개, 총 29개 테스트 통과**:

- UTF-8 디코딩·JSON 파싱·한글 원문·다운로드 헤더
- 전체 계획·수정 이력·태그·완료/취소 이력·실행 기록·개선점·다음 계획 연결 포함
- 원본 테이블 전체 값과 내보낸 배열 일치, 삭제 상태와 관련 기록 보존
- 선택한 계획에 제한되지 않는 내보내기, 계획별 집계와 돌아보기 계산 일치
- 집계 기준 시각·한국 날짜 경계·소수 시간·빈 DB·빈 계획 확인
- 내부 설정과 환경변수의 검증용 비밀 문자열 미포함, DB 읽기 전후 값 동일
- 계약의 필드 목록과 구현 일치

실제 브라우저에서 다운로드 후 파일을 여는 동작은 미확인입니다. 내보내기 개발 당시 검증은 서버 다운로드 응답을 직접 파싱하는 방식으로 수행했습니다. 가져오기는 구현하지 않았습니다. 공개 배포 현황은 위 PythonAnywhere 절에 기록했습니다.

### 실행 기록 수정과 미래 시각 검증

실행 기록 목록의 **수정**을 누르면 연결된 할 일, 시작·종료 시각, 수행 내용, 막힌 이유를 변경할 수 있습니다. 다른 계획의 할 일이나 완료된 할 일도 선택할 수 있으며 삭제된 할 일은 선택할 수 없습니다. 연결을 바꾸면 해당 할 일이 속한 계획의 실행 기록 목록으로 이동합니다.

시각은 기존과 같이 한국 시간으로 입력받고 UTC로 저장합니다. 실제 소요 시간은 서버에서 종료−시작으로 다시 계산하며 기존 분 단위 반올림 규칙을 유지합니다. **생성과 수정 모두 종료 시각이 시작 이상이고 서버 현재 시각 이하여야 합니다.** 현재 시각과 정확히 같은 종료는 허용하고 미래 종료는 거부합니다. 브라우저 시간은 판단에 사용하지 않습니다.

수정은 기존 기록 ID·생성 시각·생성 요청 ID를 유지하고 해당 행의 값만 갱신합니다. 계획·수정 이력·할 일 상태·예상 시간·다른 실행 기록은 변경하지 않습니다. 기존에 미래로 저장된 사용자 기록을 자동으로 고치지 않으며, 사용자가 수정 저장할 때 새 검증을 적용합니다. 돌아보기와 내보내기는 다음 조회부터 수정된 값을 사용합니다. 실행 기록의 별도 수정 이력이나 삭제 기능은 추가하지 않았습니다.

수정 후 원래 생성 요청을 재전송하면 현재 저장된 내용과 다른 경우 409로 거부하며 수정 내용을 되돌리거나 새 기록을 만들지 않습니다. DB 구조와 내보내기 필드는 그대로입니다.

별도 테스트 DB에서 **신규 2개 포함 총 31개 테스트 통과**. 같은 ID로 수정·재조회, 연결된 할 일 변경, 30.50분→60.50분 재계산, 생성·수정의 미래 종료 거부, 현재 시각과 같은 종료 허용, 종료가 시작보다 빠른 경우 거부와 실패 시 값 보존을 확인했습니다. 기존 테스트 자료의 시각 검증은 고정된 서버 시계로 실행해 실제 테스트 날짜에 의존하지 않게 했습니다. 실제 브라우저 클릭은 미확인입니다.
